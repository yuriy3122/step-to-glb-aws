# Security boundaries

Cognito uses authorization code with PKCE for the public SPA client. Users are created by an administrator with an immutable `custom:tenantId`; this app client cannot write that attribute. Both API Gateway and ASP.NET Core validate issuer/audience/expiry; the API additionally requires `token_use=id` and the tenant claim. Identity strings are constrained before use. Possession of another tenant's job ID or page cursor does not change the partition key used by the service.

Every job ID and attempt ID is server-generated. Input and output keys derive from authorized tenant/job/attempt identities, never client-specified keys. The API has a pooled task role, so **application authorization is an essential trust boundary**. Prefixes are organization, not IAM authorization by themselves. The worker is trusted platform code, not tenant-provided code; its role can read inputs and write results across platform tenants. A hostile worker compromise would cross that pooled role boundary. Future isolation can use scoped assumed roles/session policies or per-tenant capacity without changing the API contract.

The browser receives a short-lived capability for one object operation. It receives no AWS keys, bucket enumeration rights, table access or general S3 access. Signed Content-Length and server verification constrain accepted input size; multipart sessions issue only the declared range of part numbers and expected lengths. Incomplete uploads are aborted after one day. Versioned input and stored VersionId prevent reuse of a still-live PUT URL from replacing the accepted conversion source.

S3 Block Public Access, bucket-owner-enforced ownership, SSE-S3 encryption and TLS-only bucket policies apply to all buckets. Signature age is capped at ten minutes for CAD transfers. Output GLBs carry an S3-validated SHA-256 checksum; a matching manifest and HEAD checksum/length are required for success. Private result URLs should not be copied into logs or analytics. Browser history, referrers and token storage still deserve care: The Job API serves the React build with `Referrer-Policy: no-referrer`, a restrictive CSP and standard security headers. The SPA keeps the ID token in sessionStorage. It does not implement refresh token renewal; after the 15-minute token expires, sign in again. Tokens remain valid until expiry after local sign-out; no global logout/revocation flow is implemented.

The ALB is internal. Its ingress is restricted to the VPC Link security group; API ingress is restricted to the ALB security group. Scheduler/worker security groups have no ingress. API, scheduler and Batch instances use private subnets and HTTPS egress. S3/DynamoDB use gateway endpoints; NAT enables other AWS API calls, public Cognito metadata and ECR. Internal ALB-to-API traffic uses HTTP inside these restricted network boundaries; introduce private TLS if compliance requires encryption on that hop.

Distinct IAM roles serve API, scheduler, worker, stream Lambda, recovery Lambda, ECS execution, Batch service, Batch instances and EventBridge Scheduler. Policies scope table, buckets, queues, logs, job definition and queue resources. Batch DescribeJobs/ListJobs require wildcard resources in this reference policy. The AWS-managed ECS execution/instance and Batch service policies carry their documented broader permissions. No static AWS credentials are in source, configuration, images or CloudFormation.

Containers run as non-root. API/scheduler root filesystems are read-only, diagnostics ports are disabled, native execution uses argument lists without a shell, and the worker stores temporary files in its own generated directory. Batch instance root storage is encrypted and IMDSv2 is required. Native CAD parsers process untrusted input: use image scanning, memory/CPU/time limits, patched base images and fixture regression tests. No claim is made that a CAD kernel can safely execute arbitrary malicious input without a vulnerability.

Local mode is exclusively a loopback Development convenience with one fixed tenant and disk-stored random URL signing key. It must not be exposed as a production authentication mechanism. IAM, Cognito, S3 CORS and cross-account deployment permissions still require live AWS validation.
